# 開発者向け引き継ぎ資料

## 全体の流れ

```
LINE ──Webhook──→ /api/line/webhook ─┐  署名検証 → DBに保存（まず保存）→ キーワードでルート判定
Gmail ─GAS(1分)─→ /api/mail/ingest ──┤
                                     ├─ route=urgent → after() で即処理（同じ関数内）
                                     └─ route=normal → pg_cron（1分ごと）→ /api/cron/process-queue

処理（src/lib/process.ts）：確保（claim_inquiries）→ ① Claude で分類 → ② Slack 投稿 → ③ クレームなら部長に LINE プッシュ
```

構成図：[architecture.png](./architecture.png)（技術版）／[architecture-simple.png](./architecture-simple.png)（非エンジニア向け）

## ディレクトリ構成

| パス | 役割 |
|---|---|
| `src/app/api/line/webhook/route.ts` | LINE Webhook の受信。署名検証 → 保存 → 緊急なら after() |
| `src/app/api/mail/ingest/route.ts` | GAS からのメール受信。署名とタイムスタンプを検証 → 保存 → 緊急なら after() |
| `src/app/api/cron/process-queue/route.ts` | キュー消化。pg_cron が毎分呼ぶ（Bearer 認証） |
| `src/lib/classify.ts` | `classifyWithClaude`：tool_choice で構造化出力。カテゴリの定義と判断ルールはここ |
| `src/lib/process.ts` | 1件の処理（手順ごとに冪等）と、キューの確保 |
| `src/lib/routing.ts` | 緊急ルート判定のキーワード（拾いすぎてOK、漏れても Cron で拾う） |
| `src/lib/urgent.ts` | 緊急ルートの after() 処理 |
| `src/lib/signature.ts` | LINE とメールの署名検証 |
| `src/lib/slack.ts` / `line.ts` | 外部APIの呼び出し（429 は RetryableError） |
| `gas/mail-forwarder.gs` | Gmail の転送スクリプト（GAS に貼り付けて使う） |
| `supabase/schema.sql` | テーブル（inquiries＝キュー）と claim_inquiries 関数 |
| `supabase/cron.sql` | pg_cron のジョブ（秘密鍵は Vault に保存） |

## 設計上の約束ごと（変更するときの注意）

| 約束 | 理由 | 壊すと起きること |
|---|---|---|
| 受信したら、処理より先に保存する | 後の処理が失敗しても問い合わせが消えない | API 障害時に問い合わせが失われる |
| `(channel, external_id)` の一意制約 | LINE の再送・GAS の重複送信を弾く | 同じ問い合わせが2回投稿される |
| 処理対象は必ず `claim_inquiries` で確保する | 緊急ルートと Cron の競合を防ぐ（FOR UPDATE SKIP LOCKED） | 二重投稿・二重通知 |
| 手順ごとに完了を記録する（category / slack_ts / line_pushed_at） | 再処理で済んだ手順を飛ばす | 再試行のたびに Slack・LINE に重複して届く |
| 署名検証は `request.text()` の生の本文で行う | JSON を整形し直すと署名が一致しない | すべて 401 になる |
| キーワードはルート判定にだけ使う | 最終的な緊急判定は Claude が行う | 「緊急ではありません」で誤って通知する |

## よくある作業

| 作業 | 手順 |
|---|---|
| **全サービスへの接続確認** | `npm run check:connections`（Slack の5チャンネルと部長の LINE に「[接続テスト]」が届く） |
| **分類精度の確認（プロンプトを変えたら必ず）** | `npm run classify:sample -- --all`（22件）または `npm run eval:headless`（Headless モードで合否判定と改善案、約 $0.2） |
| **運用チェック** | `npm run ops:check`（Headless モード。止まっている問い合わせ・通知漏れ・SLA 違反を点検し、`reports/` に Markdown で保存） |
| **SLA の実績** | `npm run show:sla` |
| **最新の問い合わせ** | `npx tsx scripts/show-inquiries.ts` |
| **Cron の動作確認** | `npm run check:cron`（テスト行を1件入れて、自動で処理されるまで待つ） |
| **AI モデルの変更** | 環境変数 `CLAUDE_MODEL`（既定は `claude-haiku-4-5`）を変えて、`npm run eval:headless` で合格を確認する |
| **カテゴリの追加** | `classify.ts` の CATEGORIES と定義 → `slack.ts` の CHANNEL_ENV → `schema.sql` の check 制約 → 環境変数 → 精度確認 |

## トークンの更新・漏洩時の対応

| 対象 | 手順 |
|---|---|
| LINE チャネルアクセストークン | LINE Developers で再発行 → `.env.local` と Vercel（`vercel env add LINE_CHANNEL_ACCESS_TOKEN production --force`）→ `vercel deploy --prod` → `npm run check:connections` |
| Slack Bot Token | api.slack.com/apps →「OAuth & Permissions」で再インストール → 同上 |
| MAIL_INGEST_SECRET | `openssl rand -hex 32` で新しく作る → Vercel と GAS のスクリプト プロパティの両方を更新（GAS の `checkSecret` で長さ=64 と指紋を確認） |
| CRON_SECRET | 新しく作る → Vercel を更新 → `supabase/cron.sql` を新しい値で SQL Editor から再実行 |

## 障害時の切り分け

| 症状 | 確認する場所 |
|---|---|
| LINE の問い合わせが DB に入らない | LINE Developers の Webhook「検証」→ 成功しなければ Vercel のログ（`vercel logs --since 1h`）で 401 か 500 かを見る |
| メールが DB に入らない | GAS の「実行数」で `pollInbox` のログを見る。401 なら秘密鍵の不一致（`checkSecret`） |
| DB に入るが Slack に届かない | `npx tsx scripts/show-inquiries.ts` の last_error。pg_cron の実行履歴は SQL Editor で `select * from cron.job_run_details order by start_time desc limit 10;` |
| 全体の健康状態 | `npm run ops:check` |

## 開発中に詰まったところ

- Supabase の URL に `/rest/v1/` が付いていると、RPC だけが失敗する（件数の取得は通ってしまう）→ コード側でオリジンだけを使うようにした
- GAS のスクリプト プロパティに、秘密鍵ではなくコマンドの文字列を貼ってしまい、署名が一致しなかった → `checkSecret` で長さと指紋を比べて特定した
- `vercel project update --framework` は `--yes` を付けないと反映されない
- Vercel のプレビュー環境はデプロイ保護により、外部からの Webhook が届かない → 本番URLを使う
- Next.js 16 の型（LayoutProps）は `next typegen` を実行しないと `tsc` が通らない
